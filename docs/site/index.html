VeriFlow Agency

VeriFlow Agency je nástroj příkazové řádky, který nad jedním repozitářem opakovaně spouští agenty Claude Code podle metody zapsané přímo v projektu. Výstup každého běhu prochází deterministickou kontrolou, rozhodnutí o jednotlivých nálezech se ukládají jako markdown vedle kódu a další běh je dostane na vstupu. Nástroj zároveň počítá, jak velká část nálezů se ukázala jako oprávněná.

VeriFlow Agency is a command-line tool that repeatedly runs Claude Code agents over a single repository, following a method written down in the project itself. The output of every run passes through a deterministic check, decisions about individual findings are stored as markdown next to the code, and the next run receives them as input. The tool also measures how many findings turned out to be justified.

Proč Agency vzniklaWhy Agency exists

Claude Code řeší jednotlivé úkoly dobře, ale mezi relacemi si nedrží kontext. Po zavření okna nezůstane záznam o tom, co agent navrhl, co z toho bylo přijato a co uživatel zamítl s odůvodněním, že jde o záměr. Při dalším běhu proto může stejný návrh přijít znovu, protože nemá odkud vědět, že už jednou padl.

Druhým důsledkem je, že se přínos takové práce nedá vyhodnotit. Bez záznamu o jednotlivých nálezech a o jejich dalším osudu nelze říct, jaká část z nich byla pravdivá, které otázky se vyplatí klást a které přidávají jen šum, ani jestli úprava instrukcí něčemu pomohla. Zbývá dojem z posledního běhu, který se s odstupem špatně ověřuje.

Agency doplňuje právě tuhle vrstvu: paměť běhů, kontrolu výstupu a měření výsledků. Nic z toho nedělá model, všechno obstarává nástroj kolem něj.

Claude Code handles individual tasks well, but it keeps no context between sessions. Once the window is closed, nothing records what the agent proposed, what was accepted, and what the user rejected as deliberate. The same proposal can come back in the next run, because there is nowhere for it to learn that it was already turned down.

A second consequence is that the value of the work cannot be evaluated. Without a record of individual findings and what happened to them, there is no way to say how many of them were true, which questions are worth asking and which only add noise, or whether editing the instructions improved anything. What remains is an impression from the most recent run, which is hard to verify later.

Agency adds exactly that layer: a record of runs, a check on the output, and measurement of the results. None of it is done by the model; it is all handled by the tooling around it.

Co Agency jeWhat Agency is

Specialista je v Agency adresář ve zdrojích projektu. Leží tam, kde Claude Code už skilly hledá, takže k jeho zavedení není potřeba účet, plugin ani další služba:

In Agency, a specialist is a directory in the project's source tree. It sits where Claude Code already looks for skills, so setting one up needs no account, no plugin and no extra service:

.claude/skills/agency-review-graph/
  pack.json     ← co potřebuje vědět nástroj← what the tool needs to know
  SKILL.md      ← metoda a fakta o tomhle projektu← the method and this project's facts
  references/   ← delší podklady← longer material

Takovému adresáři se říká pack. Vychází ze skillu, tedy z adresáře s instrukcemi, které si Claude Code načte, když jsou pro daný úkol potřeba, a přidává k němu soubor pack.json. Z něj nástroj pozná, jaké příkazy smí běh spouštět, jaký rozpočet je pro pack obvyklý a kam se mají posílat nálezy.

Pack se commituje jako každý jiný zdrojový soubor a reviduje se v pull requestu. Popisuje jeden konkrétní projekt, jeho staging, jeho board i jeho pravidla, takže se do dalšího projektu kopíruje celý a fakta se v kopii přepíšou; žádná sdílená konfigurace mezi projekty nevzniká.

Druhou částí je příkaz agency, který pack spustí, hlídá jeho průběh a zaznamená výsledek. Claude Code přitom nenahrazuje, pouze řídí jeho běh, takže model zůstává stejný a mění se jen to, co běh obklopuje.

Such a directory is called a pack. It builds on a skill, a directory of instructions Claude Code loads when a task calls for them, and adds a pack.json file. From that file the tool learns which commands the run may execute, what budget is normal for the pack, and where findings should be sent.

A pack is committed like any other source file and reviewed in a pull request. It describes one specific project, its staging, its board and its rules, so moving it to another project means copying the whole thing and rewriting the facts in the copy; no configuration ends up shared between projects.

The second part is the agency command, which starts a pack, watches the run and records the result. It does not replace Claude Code but drives it, so the model stays the same and only what surrounds the run changes.

Commitovaná paměťCommitted memory

Nálezy, rozhodnutí a poznámky jednotlivých packů leží v .agency/knowledge/ jako markdown. Přečte je kolega, běžná session i člověk, který se k projektu vrátí po roce.

Findings, decisions and each pack's own notes live in .agency/knowledge/ as markdown. A colleague can read them, so can a plain session, and so can someone returning to the project a year later.

Kontrola nálezůChecking findings

Nález odkazující na soubor, který v daném commitu neexistuje, se dál neposílá. Rozhodnutí je deterministické a nepotřebuje k němu druhý model.

A finding pointing at a file that does not exist at that commit goes no further. The decision is deterministic and needs no second model.

MěřeníMeasurement

Nástroj sleduje precision, tedy podíl nálezů, které se po rozhodnutí ukázaly jako oprávněné, a člení ji podle dimenzí, modelů a verzí metody.

The tool tracks precision, the share of findings that turned out to be justified once decided, broken down by dimension, model and version of the method.

Rozdíl proti samostatnému skilluHow this differs from a plain skill

Stejnou práci lze zadat i obyčejným skillem a jako začátek to dává smysl, protože pack ze skillu vychází. Odlišnost se projeví až ve chvíli, kdy běh skončí: po skillu nezůstane žádný záznam, zatímco pack ukládá nálezy, rozhodnutí i důvody, proč něco branou neprošlo.

The same work can be handed to an ordinary skill, and as a starting point that makes sense, since a pack builds on a skill. The difference shows up when the run ends: a skill leaves no record behind, whereas a pack stores findings, decisions and the reasons why something did not pass the gate.

Kdy se Agency nevyplatíWhen Agency is not worth it

Na jednorázovou práci je samostatný skill vhodnější, protože je jednodušší a k danému účelu stačí. Agency se vyplatí až tam, kde se stejná práce nad stejným repozitářem opakuje a je potřeba vědět, jestli se její výsledky v čase zlepšují.

For one-off work a plain skill is the better choice: it is simpler and it is enough. Agency starts to pay off where the same work is repeated over the same repository and someone needs to know whether the results are improving over time.

Jak probíhá běhHow a run works

Běh spouští jediný příkaz a skládá se z pěti fází. Model pracuje jen ve druhé z nich, zbytek obstarává nástroj.

A run is started by a single command and consists of five phases. The model works only in the second one; the tool handles the rest.

agency run review-graph --pr 479 --unattended --wait
  1. Příprava Nástroj vytvoří jednorázový worktree nad commitem daného pull requestu, z code grafu zjistí, čeho se změna dotýká, a přiloží paměť projektu: co se v něm už dřív našlo, kde a co bylo zamítnuto.
  2. Běh Spustí se agent. Kromě promptu dostane seznam příkazů, které smí spustit, a v system promptu i výčet nálezů, které projekt už jednou zamítl, s pokynem nehlásit je znovu.
  3. Kontrola Výstup agenta projde deterministickou bránou. Zahodí se nález odkazující na neexistující soubor nebo na řádek za koncem souboru, nález bez důkazu i nález citující příkaz, který ve skutečnosti neproběhl. Nic se přitom nemaže, zahozený nález zůstává v záznamu běhu i s důvodem.
  4. Rozhodnutí Nálezy, které branou prošly, odejdou na board, tedy do nástroje pro sledování úkolů, který projekt používá. Pokud projekt board nemá, zůstanou v commitované paměti. O každém rozhoduje člověk nebo navazující pack a u zamítnutí se vybírá jeden z pěti důvodů.
  5. Zápis do paměti Rozhodnutí se uloží do commitované stopy a příští běh ho dostane na vstupu, takže se stejný nález nemusí posuzovat podruhé.
  1. Preparation The tool builds a throwaway worktree at that pull request's commit, reads the blast radius out of the code graph, and attaches the project's memory: what has been found before, where, and what was rejected.
  2. The run The agent starts. Besides the prompt it receives the list of commands it may execute, and in its system prompt the findings this project has already rejected, with instructions not to report them again.
  3. The gate The agent's output goes through a deterministic check. A finding pointing at a missing file or a line past the end of one is dropped, as is a finding without evidence or one citing a command that never ran. Nothing is deleted in the process: a dropped finding stays in the run record together with its reason.
  4. The decision Findings that pass the gate go to the board, the issue tracker the project uses. If the project has no board, they rest in the committed memory. Each one is decided by a person or by a downstream pack, and a rejection picks one of five reasons.
  5. Writing to memory The decision is stored in a committed trail and the next run receives it as input, so the same finding does not have to be judged twice.
Dohled nad běhemSupervision of a run

Ve výchozím nastavení běh probíhá pod dohledem: je vidět v terminálu a dá se do něj zasáhnout. Bez dozoru běží jen na výslovné vyžádání a i tehdy smí pack spouštět pouze příkazy vypsané v jeho pack.json.

By default a run is attended: it is visible in the terminal and can be interrupted. It runs unattended only when explicitly asked for, and even then a pack may execute only the commands listed in its own pack.json.

Brána a paměť projektuThe gate and project memory

Kontrolní bránaThe gate

Brána nehodnotí, jestli je nález chytrý nebo užitečný. Ověřuje jen to, jestli vůbec může být pravdivý: zda existuje soubor, na který ukazuje, zda sedí číslo řádku a zda proběhl příkaz, o který se nález opírá. Halucinovanou cestu k souboru odhalí statická kontrola bez modelu, zatímco kontrola dalším modelem by stála dvojnásobek při nižší spolehlivosti.

Výsledek je proto opakovatelný a dva lidé nad týmž během dostanou totéž. Zahozené nálezy se zároveň neztrácejí: leží vedle běhu i s důvodem zahození, takže jde zpětně posoudit, jestli brána nevyřazuje víc, než má.

The gate does not judge whether a finding is clever or useful. It only checks whether it can be true at all: whether the file it points at exists, whether the line number fits, and whether the command it rests on actually ran. A hallucinated file path is caught by a static check without a model, whereas checking with another model would cost twice as much and be less reliable.

The result is therefore repeatable, and two people looking at the same run get the same answer. Dropped findings are not lost either: they sit beside the run together with the reason they were dropped, so it is possible to review whether the gate is discarding more than it should.

Paměť projektuProject memory

Všechno, co si pack pamatuje, je markdown commitovaný do repozitáře projektu. Nepoužívá se databáze, cloudová služba ani soubor v domovském adresáři uživatele.

Má to tři důsledky. Paměť si přečte kdokoli i bez tohoto nástroje, dá se revidovat v pull requestu jako každá jiná změna a v projektu zůstane i tehdy, když se Agency přestane používat.

Everything a pack remembers is markdown committed to the project's repository. No database, no cloud service, no file in the user's home directory.

That has three consequences. Anyone can read the memory without this tool, it can be reviewed in a pull request like any other change, and it stays in the project even if Agency is dropped.

Referenční packyReference packs

Následující packy už existují jako referenční kopie. Nejsou to hotové produkty použitelné v libovolném projektu, protože každý z nich nese fakta o jednom konkrétním repozitáři. Slouží spíš jako vzor, podle kterého se dá napsat vlastní pack.

The packs below already exist as reference copies. They are not finished products usable in any project, because each of them carries the facts of one specific repository. They serve as patterns for writing your own.

review-graph

Recenzent pull requestu. Kromě diffu se ptá code grafu, čeho se změna ještě dotkne, co nemá test a co už nikdo nevolá.

A pull-request reviewer. Besides the diff it asks the code graph what else the change reaches, what has no test, and what nothing calls any more.

qa

Prochází běžící staging v čistém prohlížeči jako předem popsaná persona. Každý nález nejdřív zreprodukuje a teprve pak zapíše.

Walks the running staging app in a clean browser as a written-out persona. Every finding is reproduced first and only then written down.

po

Product owner. Porovná board s plánem, rozhodne jednotlivé položky a rozhodnutí zapíše přímo na board, ne do reportu.

A product owner. Compares the board against the plan, decides each item, and writes the decision onto the board rather than into a report.

legal

Právní kontrola proti znění předpisu s citací primárního zdroje. Hlásí i povinnosti, které si produkt uložil sám, aniž je zákon vyžaduje.

A legal pass against the wording of the law, citing the primary source. It also reports duties the product imposed on itself that the law does not require.

ceo

Strategický partner zakladatele. Přečte roadmapu i veřejný web, navrhne nejvýš tři sázky a připraví texty k odeslání.

A founder's strategy partner. Reads the roadmap and the public web, proposes at most three bets, and drafts the messages to send.

verify

Ověřovací pack. Otevře kód pod nálezem jiného packu a odvodí tvrzení znovu z kódu, ne z textu nálezu. Vlastní nálezy nehlásí.

A verification pack. It opens the code under another pack's finding and derives the claim again from the code, not from the finding's wording. It reports no findings of its own.

Jediný obecný pack je author, který píše ostatní packy; ten se instaluje rovnou. Packy se dají také zřetězit tak, že první nálezy vytvoří a druhý je posoudí:

The only generic pack is author, the one that writes the others; it is installed out of the box. Packs can also be chained, so that the first produces findings and the second judges them:

agency chain review-graph verify --pr 479
agency chain review-graph po --pr 479 --prompt "dává to produktově smysl?"
agency chain review-graph verify --pr 479
agency chain review-graph po --pr 479 --prompt "does this make product sense?"

Vytvoření vlastního packuWriting your own pack

Pack se nepíše ručně v JSONu. Zadáním je věta o tom, koho projekt potřebuje, a zbytek proběhne jako rozhovor s packem author.

A pack is not written by hand in JSON. The input is a sentence describing who the project needs, and the rest happens as a conversation with the author pack.

agency run author --prompt "hlídač databázových migrací —
  zajímá mě všechno, co se nedá vrátit zpátky"
agency run author --prompt "a watcher for database migrations —
  anything that cannot be rolled back"
  1. Načtení projektu Pack si projde jazyk, stack, CI, dokumentaci, případný board a hlavně to, co už stávající packy pokrývají, aby nový pack nehlásil totéž podruhé.
  2. Doplňující otázky Místo dotazníku se ptá jen na fakta, která z repozitáře nevyčte: kde běží staging, co v daném týmu znamená nevratná změna a koho mají nálezy zajímat.
  3. Dohoda o dimenzích Dimenze je jedna otázka, jejíž odpověď může vyjít nepravdivě. „Kvalita kódu“ tuhle podmínku nesplňuje, „migrace, která maže sloupec bez zálohy“ ano. Na formulaci dimenzí stojí použitelnost celého packu.
  4. Zápis adresáře Výsledek zůstane necommitovaný v pracovním stromě. Review probíhá přes git: diff se přečte jako u každé jiné změny a commit zůstává na uživateli.
  1. Reading the project The pack goes through the language, stack, CI, docs, any board, and above all what the existing packs already cover, so the new one does not report the same thing twice.
  2. Follow-up questions Instead of a questionnaire, it asks only for facts the repository cannot answer: where staging runs, what counts as an irreversible change in this team, and who should care about the findings.
  3. Agreeing the dimensions A dimension is one question whose answer can come back false. “Code quality” does not meet that condition; “a migration that drops a column without a backup” does. How the dimensions are phrased decides how useful the whole pack is.
  4. Writing the directory The result is left uncommitted in the working tree. Git is the review: the diff is read like any other change and the commit stays with the user.
Proč pack píše agentWhy an agent writes it

Pack je zdrojový kód a jeho psaní je běžná práce pro agenta. Podstatná část hodnoty přitom není v pack.json, který by vygenerovala i šablona, ale v sekci Project facts a ve formulaci dimenzí. Ty vzniknou jedině tak, že se někdo zeptá a člověk odpoví.

A pack is source code, and writing source code is ordinary work for an agent. Most of the value is not in pack.json, which a template could generate too, but in the Project facts section and in how the dimensions are phrased. Those only come about by someone asking and a person answering.

HarnessThe harness

Do léta 2026 uměl nástroj vypsat větu „dimenze reuse: precision 0,2“. Údaj byl pravdivý, ale nevedl k žádné akci. Mezi číslem a lepší metodou nebyla jiná cesta než člověk, který si na to vzpomene, otevře SKILL.md a něco v něm přepíše, přičemž nemá jak zjistit, jestli tím pomohl.

Harness je souhrnné označení pro vrstvu, která tuhle cestu doplňuje. Nedělá agenta autonomnějším, ale kalibrovaným: běh o sobě zaznamenává dost údajů na to, aby šlo posoudit, za jakých podmínek vznikl a jak dopadl.

Until the summer of 2026 the tool could print the line “dimension reuse: precision 0.2”. The figure was true, but it led nowhere. Between a number and a better method there was no path except a person remembering, opening SKILL.md and editing something, with no way to tell whether the edit helped.

The harness is the collective name for the layer that supplies that path. It does not make the agent more autonomous, it makes it calibrated: a run records enough about itself to judge under what conditions it happened and how it turned out.

Blokovaný běhBlocked runs

Běh, který narazil na vypnutý staging, skončí ve stavu blocked s uvedeným důvodem. Dřív se takový konec nedal odlišit od běhu, který poctivě nic nenašel.

A run that hits a dead staging server ends in the blocked state with the reason given. Previously such an ending was indistinguishable from a run that honestly found nothing.

Ověřování citacíVerified citations

Pokud se nález odvolává na výstup nějakého příkazu, nástroj ověří, že příkaz během běhu opravdu proběhl. Do té doby šlo jen o tvrzení.

If a finding cites the output of a command, the tool checks that the command actually ran during the run. Until now that was only a claim.

Oprava ještě během běhuFixes inside the run

Špatně zapsaný nález se agent dozví ještě před koncem běhu a může ho opravit. Dřív ho brána zahodila až po jeho ukončení.

The agent learns about a badly written finding before the run ends and can fix it. Previously the gate dropped it only after the agent was gone.

Průběžná upozorněníWarnings while it happens

Zacyklení, odmítané příkazy nebo překročení deklarovaného rozpočtu nástroj ohlásí v okamžiku, kdy nastanou, případně i na telefon.

A loop, refused commands or a run past its declared budget are reported the moment they occur, on a phone as well if needed.

Otisk kontextu běhuA fingerprint of the context

Každý běh si ukládá otisk použité metody i pravidel projektu, takže otázku „od úterý soudí hůř“ lze zodpovědět z dat.

Every run stores a fingerprint of the method it used and of the project's rules, so “it has judged worse since Tuesday” becomes a question the data can answer.

Údaje o vzorkuThe size of the sample

U každého čísla o ceně je uvedeno, z kolika běhů pochází. Průměr přes vzorek, kde polovina záznamů data nemá, je zavádějící.

Every cost figure states how many runs it came from. An average over a sample where half the records have no data is misleading.

Smyčka zlepšováníThe improvement loop

Metoda se zlepšuje ve třech krocích, mezi kterými stojí rozhodnutí člověka. Žádné skryté učení ani doučování modelu se přitom neděje, veškerá změna je vidět jako diff v repozitáři.

The method improves in three steps with a person's decisions in between. No hidden learning and no model training happens; every change is visible as a diff in the repository.

agency metrics --for-author review-graph   1 · výsledky packu1 · the pack's results
agency run author --revise review-graph    2 · diff do SKILL.md2 · a diff into SKILL.md
agency replay --pack review-graph          3 · kontrola regresí3 · regression check
  1. Brief o dosavadních výsledcích První příkaz nevypisuje grafy, ale shrnutí slabých míst metody: která dimenze má nízkou precision a zároveň dost rozhodnutých nálezů, aby to něco znamenalo, která už dvacet běhů nenašla nic, na čem nálezy nejčastěji padají a jaké konkrétní nálezy obstály a neobstály.
  2. Revize metody Druhý příkaz spustí author v režimu revize. Dostane brief a zapíše diff do SKILL.md. Každá změna se musí opřít o konkrétní řádek briefu; změna bez takové opory se nepřijímá. Pod deseti rozhodnutými nálezy se revize vůbec nespustí.
  3. Přehrání a kontrola regresí Třetí příkaz spustí pack znovu nad stejným commitem s aktuální metodou a porovná výsledek s tehdejšími rozhodnutími. Platí jedno pravidlo bez výjimek: vrátí-li se nález, který už byl jednou zamítnut, jde o regresi a revize neprojde.
  1. A brief on the results so far The first command prints no charts but a summary of the method's weak spots: which dimension has low precision while having enough decided findings for that to mean anything, which has found nothing in twenty runs, what findings most often fail on, and concrete examples of what held up and what did not.
  2. Revising the method The second command runs author in revise mode. It receives the brief and writes a diff into SKILL.md. Every change has to rest on a specific line of the brief; a change without that support is not accepted. Below ten decided findings a revision does not start at all.
  3. Replay and regression check The third command runs the pack again over the same commit with the current method and compares the result against the decisions made back then. One rule holds without exception: if a finding that was once rejected comes back, that is a regression and the revision does not ship.
Proč metoda leží v repozitářiWhy the method lives in the repository

Existují systémy, které si o agentovi vedou vlastní „instinkty“ s číselnou konfidencí kdesi mimo repozitář uživatele. Takové záznamy nikdo nereviduje a v praxi je nikdo nečte. Diff v SKILL.md se naproti tomu prochází ve verzovacím systému jako každá jiná změna, takže je vidět, co přesně se v metodě změnilo a proč.

Some systems keep their own “instincts” with a numeric confidence somewhere outside the user's repository. Nobody reviews those records and in practice nobody reads them. A diff in SKILL.md, by contrast, is reviewed in version control like any other change, so it is clear what changed in the method and why.

Co Agency záměrně neděláWhat Agency deliberately does not do

Následující body nejsou chybějící funkce, ale rozhodnutí o návrhu. Vyplatí se je znát dřív, než na ně někdo narazí v provozu.

The points below are not missing features but design decisions. It is worth knowing them before running into them in practice.

NeděláProč
Konfigurační souborNový údaj patří buď do pack.json jako zdroj projektu, nebo do záznamu běhu jako fakt o tom, co se stalo. Konfigurace navíc znamená soubor, který musí někdo udržovat.
Data v domovském adresářiŽádné ~/.agency/. Co platí o projektu, patří do projektu, jinak to nejde revidovat ani předat dál.
Model v bráněBrána musí být opakovatelná. Kontrola dalším modelem stojí dvojnásobek a je méně spolehlivá.
Ukončení běhu podle odhaduNástroj varuje, zapíše a nechá běh doběhnout. Jedinou výjimkou je trojnásobek rozpočtu, který si pack sám deklaroval, což už odhad není.
Commit za uživateleNový pack ani revizi nástroj necommituje. Review probíhá přes git a zůstává na člověku.
Tichý souhlasNeopravený nález se nepovažuje za přijatý. Do metrik vstupují jen výslovná rozhodnutí.
Not doneWhy
A configuration fileA new value belongs either in pack.json as project source, or in the run record as a fact about what happened. Configuration also means a file somebody has to maintain.
Data in the home directoryNo ~/.agency/. What is true about a project belongs in the project, otherwise it can be neither reviewed nor handed over.
A model in the gateThe gate has to be repeatable. Checking with another model costs twice as much and is less reliable.
Killing a run on an estimateThe tool warns, records, and lets the run finish. The single exception is three times the budget the pack declared for itself, which is no longer an estimate.
Committing on the user's behalfNeither a new pack nor a revision is committed by the tool. Git is the review and it stays with the person.
Treating silence as consentAn unfixed finding does not count as accepted. Only explicit decisions reach the metrics.

Instalace a první běhInstallation and first run

Potřebné jsou git, uv a Claude Code. Recenzent navíc vyžaduje gh a code graf, QA prohlížeče pro Playwright. Příkaz agency doctor vypíše, co chybí, ještě před prvním během.

You need git, uv and Claude Code. A reviewer also requires gh and a code graph, QA needs Playwright's browsers. The agency doctor command lists what is missing before the first run.

pwsh scripts/install.ps1           1 · jednou na stroji

cd <tvůj-projekt>
agency init                        2 · zkopíruje pack `author`
agency doctor                      3 · kontrola prostředí

agency run author --prompt "…"     4 · vytvoření vlastního packu
agency run <jméno>                 5 · spuštění packu
pwsh scripts/install.ps1           1 · once per machine

cd <your-project>
agency init                        2 · copies the `author` pack
agency doctor                      3 · environment check

agency run author --prompt "…"     4 · write your own pack
agency run <name>                  5 · run the pack

Po prvním běhu jsou podstatné tři příkazy. agency findings vypíše nalezené položky a to, kam odešly, agency triage accept|reject zapisuje rozhodnutí, ze kterých čerpá celá smyčka zlepšování, a agency metrics ukazuje dosavadní výsledky. Totéž jde ovládat z panelu ve VS Code, kde jsou nálezy zobrazené přímo u příslušného řádku kódu.

After the first run, three commands matter. agency findings lists what was found and where it went, agency triage accept|reject records the decisions the whole improvement loop feeds on, and agency metrics shows the results so far. The same is available from the VS Code panel, where findings appear next to the relevant line of code.

Časté otázkyCommon questions

Nahrazuje Agency Claude Code?Does Agency replace Claude Code?

Ne. Claude Code nebo Codex zůstává tím, co běh provádí. Agency běh připraví, hlídá jeho průběh, prožene výstup bránou a uloží výsledek. Bez Claude Code se nespustí.

No. Claude Code, or Codex, remains what executes the run. Agency prepares the run, watches it, puts the output through the gate and stores the result. Without Claude Code it does not start.

Odesílá nástroj někam data?Does the tool send data anywhere?

Sama Agency nikam. Běží lokálně pod přihlášením uživatele a všechno, co vytvoří, zůstává v repozitáři. Do modelu jde totéž, co by šlo při ručním spuštění Claude Code.

Agency itself sends nothing. It runs locally under the user's own login and everything it produces stays in the repository. What reaches the model is the same as what would reach it if Claude Code were started by hand.

Kolik to stojí?What does it cost?

Náklady odpovídají běhům modelu. Od fáze 12 umí agency metrics spočítat cenu na jeden nález, který došel na board. Každý pack navíc deklaruje, jaký běh je u něj obvyklý, a nástroj upozorní, když ho běh překročí.

The cost is the cost of the model runs. Since phase 12, agency metrics can compute the price per finding that reached the board. Each pack also declares what a normal run looks like for it, and the tool warns when a run exceeds that.

Co když packu nedůvěřuji?What if I do not trust a pack?

Dá se spustit pod dohledem a zřetězit s packem verify. Po dvou třech týdnech existují čísla, podle kterých se dá důvěra posoudit. Dokud pack nemá deset rozhodnutých nálezů, revize metody se nespustí, aby se metoda neupravovala podle náhodného vzorku.

Run it attended and chain it with the verify pack. After two or three weeks there are numbers to judge by. Until a pack has ten decided findings, a revision of the method will not start, so the method is not tuned against a random sample.

Dá se pack spustit bez dozoru?Can a pack run unattended?

Ano, ale je to volba, ne výchozí stav. Pack přitom smí spouštět jen příkazy, které má vypsané, a běh bez dozoru umí oznámit, že narazil na překážku, místo aby skončil bez vysvětlení.

Yes, but it is a choice rather than the default. A pack may still only run the commands it lists, and an unattended run can report that it hit an obstacle instead of finishing without explanation.

Co když projekt nemá board?What if the project has no board?

Nálezy zůstanou v commitované paměti a předávají se přes git. Pack bez nastaveného sink je normální stav, ne nedodělek.

Findings stay in the committed memory and travel through git. A pack with no sink configured is a normal state, not an unfinished one.
