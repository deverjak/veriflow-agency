# Graph-augmented PR review — main-panel

A pull request review with **evidence-backed** findings. The structural signal a diff alone cannot give — blast radius, affected stored flows, missing function-level tests — comes from `code-review-graph`.

**The output is not a comment. The output is `findings.json`.** A PR comment or a GitHub Project item is derived from it and optional, produced later by `agency export`, not by this skill. When a sink fails or is never run, the finding is not lost — that is the whole reason this pack exists.

## Project facts

Read this section instead of a configuration file — there isn't one.

- **Rules:** `CLAUDE.md#rules-that-will-bite-you` in the project root — read it whole, it is the input to the `repo-rules` dimension.
- **Documentation map:** `CLAUDE.md#where-the-truth-lives` — open only the sections that match the touched paths.
- **What CI does:** `npm run verify` (typegen, typecheck, lint, i18n checks, unit tests, `next build`). Used to drop findings CI would catch anyway — never run it yourself.
- **Language:** findings are in Czech. This document is in English.
- **Worktree:** a disposable checkout named `../main-panel-review-pr-<n>-<provider>` — never the user's own working copy.

## What you get ready

`agency run review-graph` already did the deterministic part and built the run directory. **Do not do it again.** Read:

```
<RUN_DIR>/context.json     PR metadata, the list of files to review
<RUN_DIR>/evidence/        graph signal — detect-changes, impact, dead-code, graph-capabilities
<RUN_DIR>/run.json         the run record you complete at the end
```

`context.json` carries, among other things:

| Key | Meaning |
|---|---|
| `worktree` | absolute path to the disposable worktree on the PR's head — **read files from here**, not from the user's working copy |
| `target.kind` | `pull-request` (open) or `merged-pull-request` (retrospective audit) |
| `target.headRefOid` / `baseRefOid` | the exact commits being reviewed against |
| `files[]` | files after filtering out lockfiles, generated files and snapshots |
| `review.dimensions` | which dimensions to run |
| `review.minScore` | the score threshold |
| `prompt` | optional free-text instruction from the person who started the run — what to focus this review on |
| `by` | how to sign a decision on a finding (`agency triage … --by <by>`). Ready-made by the core — do not assemble it yourself. |
| `knowledge` | path to the project's committed memory (`.agency/knowledge/`) — findings across runs as markdown, start at `index.md`. Absolute on purpose: the worktree has it too, but at the PR head's version. Read-only — `findings/` is generated by `agency ingest`. |

When `context.json` is missing you are running outside `agency run`. Say so and offer `agency run review-graph --pr <n>` — do not simulate the deterministic preparation by hand, it is a source of silent mistakes.

## 1. Load the project's context

- Open `CLAUDE.md#where-the-truth-lives` and read **only** the documentation sections matching the touched paths. Do not read documentation the change does not touch.
- Read `CLAUDE.md#rules-that-will-bite-you` whole — it is the input to the `repo-rules` dimension.
- For every file in `files[]`, read the **whole content from the worktree**, not just the hunks from `gh pr diff`. The worktree has the complete file after the change, so there is no reason to reason from a truncated context.

## 2. Review by dimension, in parallel

Run the dimensions from `review.dimensions` as **parallel fresh agents**. They have no context from this conversation, so hand each one: the diff, the file list with worktree paths, the matching slice of graph signal from `evidence/`, and the documentation excerpts from step 1.

| Dimension | What it looks at | What to feed it |
|---|---|---|
| `correctness` | Logic errors, broken call sites, contract changes | `evidence/impact.json`, `evidence/detect-changes.json` |
| `tests` | Whether the PR's tests actually cover the changed behavior | `evidence/detect-changes.json` → `test_gaps[]`, `agency graph tests-for <symbol> --repo <worktree>` |
| `reuse` | Duplicate read models across layers, newly dead code, unnecessary abstraction | `evidence/dead-code.json` |
| `errors` | Swallowed errors, missing `await`, non-idempotent handlers | the diff |
| `repo-rules` | The project's own rules — **the content is the project's, not the pack's** | `CLAUDE.md#rules-that-will-bite-you` |

When `prompt` is not `null`, **go through the named area first and more thoroughly.** A prompt changes order and depth, not the rules: a finding outside the prompt is not discarded, and a finding with no evidence does not pass the gate even when the prompt explicitly asked for it.

Before any dimension calls anything suspicious, **verify it against the graph**:

```bash
agency graph locate "<name>" --repo <worktree>
agency graph neighbors <name> --direction in --repo <worktree>
agency graph tests-for <name> --repo <worktree>
```

That is exactly what turns a guess into an evidence-backed finding.

Ask through `agency graph`, never the tool directly: the answer is JSON with paths relative to the repository (the tool itself returns absolute, OS-native paths on Windows, which then fail to match the POSIX paths from `gh`), and `evidence.source` then survives a change of graph tool.

> **What the driver cannot answer does not get documented.** `evidence/graph-capabilities.json` says which questions this driver answers. When `tests-for` or `unreferenced` is missing, the dimension that stands on it **skips itself and says so in `exitReason`** — it does not guess from the diff. A missing capability is a legitimate outcome, an invented finding is not.

## 3. The deterministic gate — before the quality filter

Drop every finding that lacks **both**:

1. `file` + `line` inside a file from `files[]`
2. at least one `evidence` item — a graph fact, a rule from the documentation, a missing test, or diff content

This is not judgement, it is the schema: `finding.v1` will not validate a finding like that. Record the dropped count in `run.json` → `counts.gated`. A finding with no evidence is not a stricter finding, it is a finding nobody can verify or find again later.

## 4. Filter false positives

From what remains, drop what is:

- **pre-existing state**, not introduced by this diff — check against the hunk boundaries or `git blame` in the worktree
- **caught by CI** — `npm run verify` already does typecheck/lint/tests/build, do not re-derive it
- **deliberately silenced** — a lint-ignore comment, a documented exception
- **nitpicking with no basis** in the project's rules or in the graph
- **on a line the PR did not touch**

Score what survives 0–100 and keep `>= review.minScore`. **Zero findings is a valid result**, not a failed run.

## 5. Write `findings.json`

The only mandatory output. Into `<RUN_DIR>/findings.json`, an array of `finding.v1` objects:

```jsonc
{
  "id": "<ULID>",
  "runId": "<from run.json>",
  "pack": "review-graph",
  "dimension": "correctness",
  "severity": "high",
  "title": "One-sentence claim of what is wrong",
  "body": "Markdown: the claim plus a concrete failure scenario — inputs/state → wrong output.",
  "anchor": {
    "file": "src/foo.ts",
    "line": 142,
    "endLine": 158,
    "commit": "<all 40 characters of headRefOid>",
    "snippet": "<text of the 142..158 block from the worktree>",
    "symbol": { "name": "UserService.getUser", "range": [128, 171] },
    "body": "<the symbol's body, capped at 8 kB>"
  },
  "evidence": [
    { "kind": "graph", "detail": "3 callers at d=1, 0 tests", "source": "agency graph impact --depth 2" }
  ],
  "score": 92,
  "state": "candidate"
}
```

On the anchor, because a finding's usability a month from now stands on it:

- **`commit` is all 40 characters.** A shortened SHA can later silently point at a different line.
- **`snippet` is the whole `line..endLine` block,** not one line. A one-line snippet fails on `/**`, `}` and similar boilerplate — and a docblock starts with exactly that.
- **Fill `symbol` from the graph,** not by guessing: `agency graph locate "<name>" --repo <worktree>` returns `file`, `line` and `endLine`. It is the one layer of the anchor that survives a refactor.
- **`anchor.body`** is the safety net for a commit no longer in the clone — a squash-merge with the branch deleted is GitHub's default.

Complete `run.json`: `status`, `finishedAt`, `counts` and `cost` (provider, model, number of dimensions, duration).

And write `<RUN_DIR>/summary.md` — **at most 30 lines** in your own words: what prompt you ran with, what you examined, what you found (counts and the substance, not a list of findings), what you decided and what you recommend next. Read by a person, by the project's memory chronology, and by the next specialist building on this run. It neither replaces nor copies `findings.json` — the structured data is there, this is your voice.

## 5b. When you are running in a chain

`context.json` → `chain` is `null` for a standalone run. When it is not, you are one member of a team someone assembled deliberately, and two things apply in addition.

**You do not start other runs.** No `agency run`, no `agency chain` — the core refuses it. When the prompt mentions another specialist ("use the PO agent to find out…"), that sentence is addressed to the chain, not to you: write what you found and leave the rest to the next member.

**When someone runs after you** (`chain.position < chain.of`), also write `<RUN_DIR>/handoff.md` — a few paragraphs **for that specific person**, not a recap for the record:

- what you did not resolve and what resolving it would take,
- which findings rest on an assumption about the **product**, not the code — those are exactly the ones the next member can confirm or kill,
- where you are unsure and what you would not sign off on without a second pair of eyes.

Do not repeat the findings — they arrive as data (`evidence/upstream.json`). Write what the data does not carry. The whole file goes into the next member's prompt along with its path, so manage length for readability, not against a cap.

**When you have no findings at all, the handoff matters more, not less.** An empty `findings.json` means "I looked and there is nothing there" — that is a result, not silence. What you learned along the way about the product, the scope, or the risk belongs to the next member; otherwise they get a zero and nothing else.

## 6. Publishing happens later, and by hand

This skill's job ends at `findings.json`. Nothing here posts a PR comment or writes to a GitHub Project — that happens after a human triages the findings (`agency triage`), through `agency export --project <n>`, which is one-way and safe to run more than once (it updates by finding id, never duplicates). Do not call `gh pr comment` or `gh api` yourself.

## 7. Cleanup

`agency run` removes the worktree itself, even when the run fails. Do not delete it by hand — the CLI keeps a record of it and still needs it to compute anchors.
